# تحلیل پیش از پیاده‌سازی هم‌لیست

> **وضعیت:** مرحلهٔ کشف و تصمیم‌گیری؛ هنوز هیچ کد Next.js پیاده‌سازی نشده است. این سند، قابلیت‌ها و جریان‌ها را از هم جدا می‌کند تا پیش از شروع، محدوده و تصمیم‌های محصول تأیید شوند.
>
> **تصمیم تازهٔ کاربر:** ابتدا روی فرانت‌اند تمرکز کنیم و backend/auth/دیتابیس واقعی را به فاز بعد موکول کنیم. بنابراین فاز نخست می‌تواند UI و تعاملات را با دادهٔ آزمایشی پوشش دهد، اما هیچ‌وقت ورود، دعوت، همگام‌سازی یا ذخیرهٔ ابری را واقعی جا نمی‌زند.

## ۱. تصمیم‌های تثبیت‌شده

- نام محصول: **هم‌لیست / HamList**.
- کاربران بالقوه متنوع‌اند: فرد، خانواده، دوستان، هم‌خانه‌ای‌ها یا گروه‌های کوچک؛ محصول نباید فقط برای یک گروه خاص طراحی شود.
- پلتفرم: **PWA موبایل‌محور**، با پشتیبانی مناسب از دسکتاپ.
- زبان‌ها: فارسی و انگلیسی، با RTL/LTR کامل.
- ظاهر: زمینهٔ روشن سفید با رنگ تأکیدی بنفش؛ تم تیرهٔ سرمه‌ای/اسلیت با بنفش سرد. فونت Vazir/Vazirmatn به‌صورت محلی.
- فناوری فرانت‌اند مدنظر: **Next.js + TypeScript + Tailwind CSS + shadcn/ui**.
- خواستهٔ اصلی کاربر: پیش از شروع کدنویسی، فلوها، فیچرها و معماری مرور و تأیید شوند.

## ۲. مسئله‌ای که نسخهٔ اول باید حل کند

وقتی چند نفر از فهرست‌های پراکنده، یادداشت‌ها یا پیام‌رسان استفاده می‌کنند، معمولاً نسخهٔ معتبر، وضعیت کار و مسئولیت‌ها روشن نیست. هم‌لیست باید راهی سبک برای ساخت یک فضای خصوصی، ایجاد فهرست و همکاری با نفر دیگر فراهم کند.

### حلقهٔ اصلی ارزش

```text
ساخت فضا یا فهرست
→ افزودن چند مورد
→ دعوت یک نفر
→ عضو دوم موردی را تغییر می‌دهد یا تکمیل می‌کند
→ تغییر برای اعضای مجاز همگام می‌شود
→ گروه دوباره برای استفادهٔ واقعی برمی‌گردد
```

**فعال‌شدن پیشنهادی کاربر:** یک کاربر فضا/فهرست بسازد، دست‌کم یک مورد ثبت کند و نفر دوم دعوت را بپذیرد یا اولین تغییر مشترک را انجام دهد.

## ۳. نقشهٔ قابلیت‌ها و اولویت پیشنهادی

### P0 — MVP قابل عرضهٔ محدود

1. **ورود و حساب**
   - ساخت حساب/ورود، خروج، حفظ نشست، خطاهای قابل‌فهم و محافظت از مسیرهای خصوصی.
   - روش دقیق ورود هنوز باید انتخاب شود.
2. **فضاها**
   - فضای شخصی و فضای گروهی؛ پیش‌فرض خصوصی.
   - ساخت، تغییر نام، مشاهدهٔ اعضا، خروج از فضا و بایگانی.
   - حذف فضا فقط برای مالک و با حل وضعیت مالکیت.
3. **فهرست‌ها**
   - ساخت از قالب ساده یا خالی؛ نام‌گذاری، ویرایش، بایگانی و حذف کنترل‌شده.
   - نوع اولیه: خرید، کارهای عمومی، سفر/رویداد، خالی.
   - مرتب‌سازی/فیلتر ساده: همه، باز، انجام‌شده.
4. **موردهای فهرست**
   - افزودن سریع، ویرایش، تکمیل/بازگشایی، حذف و بازگردانی کوتاه‌مدت.
   - عنوان ضروری؛ یادداشت، مقدار/واحد و مرتب‌سازی اختیاری.
   - ثبت سازنده و زمان تغییر برای عیب‌یابی و تاریخچهٔ پایه.
5. **دعوت و همکاری**
   - ساخت لینک دعوت محدود به یک فضا؛ انقضا/ابطال و نقش مشخص.
   - صفحهٔ پیش‌نمایش دعوت: دعوت‌کننده، فضا و دسترسی پیش از پذیرش.
   - ورود/ثبت‌نام از دعوت و بازگشت به همان دعوت پس از ورود.
   - نمایش اعضا، حذف عضو توسط نقش مجاز و خروج امن.
6. **مجوزها و امنیت**
   - حداقل نقش‌ها: `owner` و `member`; نقش فقط‌خواندنی را می‌توان در MVP افزود، اما هزینهٔ تست مجوزها را بالا می‌برد.
   - هر خواندن/نوشتن در سرور بر اساس عضویت فضا مجازسنجی شود؛ مخفی‌کردن دکمه در UI کافی نیست.
   - فضاها در جست‌وجوی عمومی ظاهر نشوند؛ توکن دعوت و محتوای فهرست وارد log/analytics نشود.
7. **تجربهٔ پایه**
   - خانه، فضای خالی، جست‌وجوی نام فهرست/فضا، loading/error/empty/offline، toast و تأیید حذف.
   - همگام‌سازی تازه‌سازی‌شونده یا realtime، با نمایش وضعیت اتصال.
   - تنظیم زبان و تم روشن/تیره؛ فارسی RTL و انگلیسی LTR واقعی.
8. **PWA پایه**
   - manifest، آیکون‌ها، نصب‌پذیری، حالت standalone و به‌روزرسانی امن.
   - در قطع اینترنت، نمایش آخرین دادهٔ مجاز و آخرین زمان همگام‌سازی به‌صورت فقط‌خواندنی؛ فرم ثبت‌نشده به‌صورت پیش‌نویس محلی.
   - نوشتن آفلاین و همگام‌سازی تعارض‌دار در MVP انجام نشود.

### P1 — پس از اثبات استفادهٔ تکرارشونده

- تبدیل/نمایش موارد به‌عنوان **کار** همراه مسئول، موعد و اولویت.
- صفحهٔ «کارهای من» و فیلتر موعد/مسئول.
- یادآور داخل محصول؛ سپس اعلان مرورگر/email فقط با رضایت، ساعات سکوت و مدیریت منطقهٔ زمانی.
- فید فعالیت پایه: چه کسی چه موردی را اضافه/تکمیل کرد.
- نقش‌های گسترده‌تر، قالب‌های قابل‌ویرایش، جست‌وجوی پیشرفته و اعلان‌های قابل تنظیم.
- ویرایش یا تکمیل هم‌زمان با بازخورد زنده، فقط پس از انتخاب راهکار backend/realtime.

### P2 — فقط با شواهد تقاضا و بازبینی حقوقی/مالی

- ثبت هزینه و تقسیم مساوی/سفارشی؛ ثبت دستی تسویه، بدون انتقال پول.
- خروجی CSV، تاریخچهٔ بلندمدت، هزینه‌های تکرارشونده.
- دعوت مهمان/دسترسی موقت، فضای سازمانی، محدودیت‌های پلن و پرداخت اشتراک.

### ایده‌های قابل بررسی، نه تعهد MVP

- افزودن مورد با گفتار، اسکن بارکد، تکرار دوره‌ای، پیشنهاد خودکار موارد پرتکرار.
- عکس/فایل، واکنش، نظر، برچسب/دسته‌بندی، فعالیت تفصیلی.
- import/export از سرویس‌های دیگر، ویجت و اتصال تقویم.
- دستیار هوشمند برای ساخت فهرست یا تقسیم کار.

این‌ها جذاب‌اند، اما هرکدام ریسک حریم خصوصی، پیچیدگی یا نگهداری دارند؛ باید با مسئلهٔ واقعی و دادهٔ استفاده توجیه شوند.

## ۴. فلوهای کاربر که باید طراحی و آزموده شوند

### F1 — بازدیدکننده تا اولین فهرست

1. صفحهٔ معرفی وعدهٔ روشن و CTA واحد دارد.
2. کاربر ساخت فهرست را شروع می‌کند.
3. اگر ورود لازم است، پس از ورود به همان مقصد برمی‌گردد.
4. فضا شخصی/گروهی انتخاب می‌شود یا فضای شخصی پیش‌فرض ساخته می‌شود.
5. نام و قالب انتخاب می‌شوند؛ کاربر اولین مورد را اضافه می‌کند.
6. UI موفقیت را نشان می‌دهد و دعوت نفر دوم را پیشنهاد می‌کند، نه اینکه اجباری کند.

**حالت‌ها:** ایمیل نامعتبر، لینک ورود منقضی، قطع شبکه، برگشت به صفحه، دوبار کلیک، حساب تکراری.

### F2 — ساخت فضای گروهی

1. نام فضا و در صورت نیاز نوع استفاده/قالب انتخاب شود.
2. فضای خصوصی ساخته شود؛ مالک به‌طور واضح مشخص باشد.
3. اولین فهرست ایجاد یا از قالب انتخاب شود.
4. کاربر بتواند دعوت را اکنون رد کند و بعداً از فضای خودش بفرستد.

### F3 — دعوت و پذیرش

1. مالک «دعوت عضو» را می‌زند؛ نقش و مدت اعتبار را انتخاب می‌کند.
2. لینک تصادفی و محدود ساخته و امکان کپی/اشتراک‌گذاری داده می‌شود.
3. مهمان لینک را باز می‌کند؛ اعتبار، انقضا، لغو و عضویت قبلی بررسی می‌شود.
4. نام فضا، دعوت‌کننده و سطح دسترسی نمایش داده می‌شود.
5. کاربر وارد/ثبت‌نام می‌کند و به همان دعوت برمی‌گردد.
6. پس از پذیرش، عضویت ایجاد و صاحب فضا/اعضا به‌روز می‌شوند.

**خطاها:** دعوت لغوشده، منقضی، استفاده‌شده، حداکثر ظرفیت، عضو قبلی، دسترسی از حساب اشتباه.

### F4 — همکاری روی فهرست

1. عضو فضا فهرست را باز می‌کند؛ breadcrumb و فضا/نقش واضح است.
2. مورد را سریع اضافه می‌کند یا مورد موجود را تکمیل/ویرایش می‌کند.
3. تغییر با شناسهٔ پایدار و مجوز سمت سرور ثبت می‌شود.
4. سایر اعضا تغییر را می‌بینند؛ در حالت قطع اتصال، UI وضعیت را صادقانه نشان می‌دهد.
5. حذف با undo کوتاه؛ حذف دائمی/بایگانی از منوی جدا انجام می‌شود.

### F5 — جست‌وجو و بازگشت

1. جست‌وجو فقط فضاها/فهرست‌هایی را نشان می‌دهد که کاربر مجوز دیدنشان را دارد.
2. نتایج با نام و مسیر فضا ارائه می‌شوند؛ حالت بدون نتیجه راه بعدی دارد.
3. خانه، موارد اخیر و فهرست‌های سنجاق‌شده (در صورت تأیید) مسیر بازگشت سریع می‌دهند.

### F6 — دعوت/مدیریت عضو و مالکیت

- مالک لینک را لغو می‌کند، عضو را حذف می‌کند یا مالکیت را منتقل می‌کند.
- عضو عادی می‌تواند از فضا خارج شود؛ اگر مالک تنهاست، خروج مستلزم انتقال مالکیت یا حذف فضاست.
- اثر حذف/خروج پیش از تأیید توضیح داده شود.

### F7 — PWA، آفلاین و به‌روزرسانی

- نصب از مرورگر مناسب یا راهنمای Add to Home Screen در iOS.
- آفلاین: shell برنامه باز شود، آخرین sync timestamp نمایش داده شود، اطلاعات خصوصی فقط برای همان حساب cache شده باشد.
- تغییر ثبت‌نشده پیش‌نویس است و نباید وانمود شود برای دیگران همگام شده.
- هنگام update، فرم/کار در حال ویرایش بی‌صدا از بین نرود.
- پس از logout/account switch cache خصوصی همان کاربر پاک شود.

### F8 — تم و زبان

- انتخاب تم روشن/تیره در سربرگ؛ پایداری تنظیم در نشست‌های بعدی.
- تغییر فارسی/انگلیسی، direction، جایگاه آیکون/دکمه، اعداد، تاریخ و پیام‌های خطا را به‌درستی عوض کند.
- تصمیم باز: دنبال‌کردن ترجیح سیستم یا همیشه ترجیح ذخیره‌شدهٔ خود کاربر؟

### F9 — کار، موعد و یادآور (P1)

- کار از فهرست یا نمای «کارهای من» ایجاد شود.
- مسئول، موعد، منطقهٔ زمانی، وضعیت انجام و تغییر مسئول مشخص باشد.
- یادآور بدون اجازهٔ اعلان مرورگر همچنان داخل برنامه قابل مشاهده باشد.
- موعد منقضی، تعویق، حذف و تغییر timezone آزموده شوند.

### F10 — هزینهٔ گروهی (P2)

- مبلغ/ارز/پرداخت‌کننده/افراد مشمول/یادداشت ثبت شوند.
- سهم‌ها پیش‌نمایش و امکان اصلاح قبل از ثبت داشته باشند.
- عبارت «پرداخت واقعی انجام نمی‌شود» دائماً قابل‌مشاهده باشد.
- محاسبهٔ گردکردن و حذف عضو/بازپرداخت باید تعریف شود.

## ۵. صفحات و مسیرهای پیشنهادی

```text
/                         معرفی
/[locale]/login            ورود
/[locale]/signup           ساخت حساب
/[locale]/app              خانه
/[locale]/app/spaces       فضاهای من
/[locale]/app/spaces/[id]  جزئیات فضا و اعضا
/[locale]/app/lists/[id]   جزئیات فهرست و موارد
/[locale]/app/my-tasks     فاز P1
/[locale]/app/reminders    فاز P1
/[locale]/app/expenses     فاز P2
/[locale]/invite/[token]   پیش‌نمایش/پذیرش دعوت
/[locale]/app/settings    زبان، تم، حساب و حریم خصوصی
```

ممکن است prefix زبان با cookie/header جایگزین شود؛ قبل از کدنویسی باید انتخاب شود. هر مسیر خصوصی باید guard سمت سرور داشته باشد.

## ۶. مدل دامنهٔ پیشنهادی

```text
User
 ├─ memberships ─ Space ─ Lists ─ ListItems
 ├─ created invitations ─ SpaceInvitation
 └─ preferences (locale, theme)

SpaceMembership: user_id + space_id + role + status
SpaceInvitation: token_hash + role + expires_at + revoked_at + created_by
List: space_id + name + kind + status + position
ListItem: list_id + title + note + quantity/unit? + status + position + created_by + updated_at + version
ActivityEvent (P1): actor + entity + action + timestamp; no sensitive payload in logs
```

مبالغ و ledger از هستهٔ فهرست جدا بمانند. برای P1 می‌توان مسئول/موعد را به ListItem افزود یا یک Task مستقل ساخت؛ این تصمیم به تعریف «آیا هر فهرستی ذاتاً task است؟» بستگی دارد و باید پیش از schema نهایی حل شود.

### قواعد داده و مجوز

- `Space` مالک مشخص دارد؛ دسترسی هر `List` و `ListItem` از عضویت فضا به ارث می‌رسد.
- invite token خام در دیتابیس ذخیره نشود؛ hash و زمان انقضا/لغو ذخیره شود.
- درخواست‌ها idempotency و کنترل نسخه/تعارض داشته باشند؛ حذف روزمره soft-delete/undo باشد.
- رویدادهای analytics فقط رفتار کلی/بدون متن فهرست، email یا توکن را ثبت کنند.

## ۷. پیشنهاد معماری با استک خواسته‌شده

### فرانت‌اند

- Next.js App Router + TypeScript؛ صفحات خواندنی تا جای ممکن Server Component.
- Client Component فقط برای تعامل تعاملی: quick-add، checkbox، dialog، toast، تغییر تم/زبان، realtime.
- Tailwind CSS برای layout و spacing؛ design tokens رنگ/تم در CSS variables.
- shadcn/ui برای Button, Dialog, Sheet, DropdownMenu, Input, Checkbox, Tabs, Skeleton, Tooltip و Sonner؛ کامپوننت‌ها در مخزن خود پروژه می‌مانند و متناسب با RTL/تم اصلاح می‌شوند.
- Vazir/Vazirmatn به‌صورت local font؛ دو تم از CSS variables، نه انبوه رنگ‌های ثابت پراکنده.
- بررسی `next-intl` برای پیام‌ها و مسیرهای locale؛ همهٔ متن‌ها از catalog بیایند.

### backend — هنوز انتخاب نشده و طبق تصمیم کاربر به فاز بعد موکول است

گزینه‌های زیر فقط برای ثبت مسیر آینده‌اند؛ در فاز فعلی هیچ دیتابیس/Auth/Realtime واقعی انتخاب یا پیاده‌سازی نمی‌شود.

**گزینهٔ سریع برای MVP:** Supabase (Postgres + Auth + RLS + Realtime). مزیت: سرعت، دیتابیس relational و کانال همگام‌سازی. الزام: سیاست RLS و تست cross-user دقیق؛ کلید service-role هرگز به کلاینت نرود.

**گزینهٔ کنترل بیشتر:** PostgreSQL مدیریت‌شده + ORM (Drizzle یا Prisma) + Auth.js/Better Auth + API/Server Actions در Next.js. مزیت: کنترل کامل‌تر؛ هزینه: پیاده‌سازی auth، realtime و عملیات زیرساخت بیشتر.

**توصیهٔ موقت:** برای MVP کوچک با نیاز به همکاری زنده، Supabase را ارزیابی کنیم؛ اما قبل از تأیید بازار، میزبانی، محل داده و روش ورود، آن را قطعی نکنیم.

### مرزبندی لایه‌ها

```text
UI (App Router + shadcn)
→ domain services (validation + authorization + business rules)
→ repository/backend adapter
→ Postgres
```

- Server Action برای فرم‌ها/تغییرات داخلی مناسب است؛ route handler برای endpoint عمومی دعوت، webhook و integration.
- قواعد دسترسی در سرور/backend enforce شوند؛ صرفاً به محافظت route یا React اعتماد نشود.
- قرارداد داده/سرویس از UI جدا باشد تا انتخاب backend بعداً کل رابط را قفل نکند.

### PWA

- `app/manifest.ts`، آیکون‌های درست و قابل mask، HTTPS و standalone.
- شروع با shell caching و حالت read-only آفلاین؛ هیچ cache عمومی برای پاسخ‌های authenticated.
- service worker/update lifecycle جداگانه تست شود؛ انتخاب کتابخانهٔ Serwist یا پیاده‌سازی دستی بعد از بررسی سازگاری با نسخهٔ Next تثبیت شود.

## ۸. ساختار پوشهٔ پیشنهادی (پس از تأیید معماری)

```text
src/
  app/[locale]/(marketing)/...
  app/[locale]/(auth)/...
  app/[locale]/(product)/app/...
  app/[locale]/invite/[token]/...
  components/ui/              # shadcn
  components/hamlist/         # list, space, member, empty states
  features/auth|spaces|lists|invites/  # UI + schema + actions
  lib/auth/ lib/db/ lib/i18n/ lib/pwa/
  server/domain/ server/repositories/
messages/fa.json
messages/en.json
public/icons/
```

این فقط پیشنهاد است؛ تا زمان انتخاب backend و locale strategy فایل‌ها ساخته نمی‌شوند.

## ۹. لایه‌بندی و دروازه‌های تحویل

### Gate 0 — تأیید محصول و معماری

- MVP و first use-case مشخص شوند.
- Backend/database/auth/hosting و بازار اولیه انتخاب شوند.
- نقش‌ها، privacy، ورود/دعوت، offline boundary و هزینه تعریف شوند.
- وایرفریم‌های موبایل RTL و دسکتاپ LTR بررسی شوند.

### Gate 1 — Foundation + prototype wiring

- ایجاد Next app، TypeScript, Tailwind, shadcn, Vazir, locale, tokens و route skeleton.
- آزمون build، lint، responsive/RTL و accessibility پایه.

### Gate 2 — MVP حلقهٔ همکاری

- auth → create/join space → create list → add/check item → invite member → shared update.
- integration tests مجوزها، invite edge cases و چند کاربر.

### Gate 3 — PWA و عرضهٔ محدود

- manifest/install/service worker، read-only offline، logout/cache cleanup، telemetry امن، backup و monitoring.
- pilot محدود؛ بازبینی activation, invite acceptance, week-1 return و گزارش خطا.

### Gate 4 — گسترش

- P1 tasks/reminders؛ P2 expenses؛ سپس pricing/integrations فقط بر اساس شواهد.

## ۱۰. معیارهای پذیرش MVP پیشنهادی

- کاربر تازه بتواند حساب بسازد، فضا/فهرست بسازد و اولین مورد را در یک مسیر کوتاه اضافه کند.
- نفر دوم با دعوت معتبر بپیوندد و تغییر مشترک را ببیند.
- کاربر خارج از فضا حتی با دست‌کاری URL/API دادهٔ فضا را نبیند/تغییر ندهد.
- لینک دعوت منقضی/لغوشده/استفاده‌شده پاسخ روشن و امن بدهد.
- duplicate submit فهرست/مورد تکراری نسازد؛ خطای شبکه متن واردشده را نابود نکند.
- فهرست‌های خصوصی از cache عمومی و analytics خارج باشند؛ خروج حساب cache خصوصی را پاک کند.
- فارسی RTL و انگلیسی LTR در موبایل و دسکتاپ؛ keyboard focus و label قابل فهم.
- تم روشن سفید/بنفش و تم تیرهٔ midnight-indigo در همهٔ صفحه‌های MVP سازگار باشند.
- install/standalone درست کار کند؛ آفلاین بودن با همگام‌شدن اشتباه نشود.

## ۱۱. تصمیم‌هایی که قبل از کدنویسی باید از کاربر بگیریم

پیشنهاد پیش‌فرض در پرانتز است؛ پیش‌فرض به معنی تصمیم قطعی نیست.

1. **نقطهٔ شروع MVP:** فهرست خرید/زندگی روزمره، یا فهرست عمومی برای هر گروه؟ (هستهٔ عمومی با نمونه‌های آماده.)
2. **Backend:** Supabase یا backend سفارشی با Postgres؟ (ارزیابی Supabase برای سرعت MVP.)
3. **ورود:** ایمیل OTP/magic link، رمز عبور، یا Google/Apple؟ (ایمیل یک‌بارمصرف به‌همراه لینک دعوت؛ بازار و provider تعیین‌کننده است.)
4. **دامنهٔ نسخهٔ اول:** فقط فضا + فهرست + دعوت، یا مسئول/موعد کار هم از روز اول؟ (پیشنهاد: موردهای فهرست/تکمیل + دعوت؛ task assignment در P1.)
5. **نقش‌های MVP:** مالک + ویرایشگر، یا فقط‌خواندنی هم لازم است؟ (owner/member در MVP.)
6. **بازار و منطقهٔ داده:** کدام کشور/منطقه برای pilot؟ (برای hosting، privacy، email و پشتیبانی لازم است.)
7. **آفلاین:** در MVP فقط مشاهدهٔ آخرین sync و draft، یا نوشتن آفلاین با حل تعارض؟ (فقط مشاهده + draft.)
8. **حساب اجباری:** آیا ساخت فهرست خصوصی قبل از ثبت‌نام ممکن باشد؟ (در MVP حساب لازم، ورود از دعوت به‌خوبی ساده شود.)

پس از پاسخ این موارد، گام بعدی نهایی‌کردن PRD، نمودارهای sequence/permission و schema اولیه است؛ سپس اجازه می‌گیریم و وارد پیاده‌سازی Next.js می‌شویم.

## ۱۲. مسیر اجرایی فرانت‌اند‌اول (بر اساس تصمیم تازهٔ کاربر)

### در فاز فعلی چه می‌سازیم؟

1. **Foundation بصری:** Next.js App Router + TypeScript، Tailwind، پیکربندی shadcn/ui، فونت محلی Vazir، توکن‌های تم سفید/بنفش و midnight-indigo، RTL/LTR، layout موبایل/دسکتاپ.
2. **App shell:** سربرگ، ناوبری دسکتاپ/موبایل، وضعیت اتصال نمایشی، کنترل تم و زبان، مسیرهای اصلی.
3. **خانه:** فضای اخیر، فهرست‌ها، خلاصهٔ موارد، فعالیت نمونه و حالت‌های خالی/بارگذاری/خطا.
4. **فضا و فهرست:** جزئیات فضا و اعضای نمونه؛ ساخت/ویرایش/آرشیو فضا و فهرست در حالت demo.
5. **موردها:** افزودن، تغییر عنوان/یادداشت، تکمیل/بازگشایی، مرتب‌سازی/فیلتر، حذف و undo در دادهٔ نمونه.
6. **دعوت:** UI انتخاب نقش/انقضا، پیش‌نمایش لینک نمونه، کپی لینک؛ همراه برچسب روشن «دعوت واقعی ارسال نمی‌شود».
7. **تنظیمات:** تم و زبان؛ بخش‌های حساب فقط نمایشی تا وقتی auth واقعی انتخاب شود.
8. **Responsive + دسترس‌پذیری:** موبایل باریک، تبلت، دسکتاپ، RTL/LTR، keyboard focus، کاهش حرکت و کنتراست.

### مرز دادهٔ آزمایشی

- عملیات در یک `DemoRepository` یا adapter فرانت‌اند قرار بگیرند؛ صفحه‌ها مستقیم به localStorage یا mock JSON وابسته نشوند.
- قراردادهای آینده مثل `listSpaces`, `createList`, `updateItem`, `acceptInvite` از UI جدا باشند تا بعداً adapter واقعی جایگزین شود.
- در نسخهٔ demo، داده‌ها می‌توانند موقتاً در مرورگر بمانند؛ متن UI باید صریحاً بگوید «فقط روی این دستگاه/مرورگر».
- هیچ fake login موفق، عضویت واقعی، ایمیل/اعلان واقعی، realtime، پرداخت یا نصب‌پذیری ادعایی نداریم.
- اگر localStorage برای دادهٔ demo استفاده شد، دکمهٔ reset دادهٔ نمونه در توسعه وجود داشته باشد؛ secrets یا دادهٔ واقعی وارد آن نشود.

### فعلاً نمی‌سازیم

- دیتابیس/API/auth، ارسال دعوت به کاربر دیگر، synchronization، realtime، نقش‌های سمت سرور، push/email، نوشتن آفلاین، پرداخت.
- اجرای کامل task assignment/reminders/expenses؛ در UI نقشهٔ محصول می‌توان آن‌ها را به‌صورت «فاز بعد» نشان داد، نه دکمهٔ فعالِ گمراه‌کننده.
- انتخاب نهایی provider، host، schema یا سیاست retention.

### معیار خروج از فاز فرانت‌اند

- کاربر بتواند فلوهای demo را بدون راهنما طی کند و بازخورد UI/UX بدهد.
- هیچ اکشن نمایشی با عملیات backend اشتباه نشود.
- تم/زبان، RTL/LTR و layout در viewportهای 360، 390، 768 و 1440px بازبینی شوند.
- صفحات و stateها به قراردادهای داده وابسته به mock implementation خاص نباشند.
- پس از تأیید UI و flowها، backend جداگانه طراحی و اتصال هر feature مرحله‌بندی شود.
